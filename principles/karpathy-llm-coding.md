# Karpathy LLM 编码全局准则

> **来源**：Andrej Karpathy 2024-10 X post（id 1854883857489522876）+ multica-ai/andrej-karpathy-skills 仓库提炼 + AbdullahHameedKhan/karpathy-ponytail-skills（懒惰梯 + 根因战术，2026-07-05 吸收）。
> **定位**：本 skill 的**全局 LLM 编码行为准则**，与项目业务上下文（如有）平级（前者管"业务规则显性化"，本准则管"LLM 编码动作准确性"）。
> **适用范围**：所有项目，所有 phase。即使 PM 关闭 项目业务上下文，本准则仍生效。

---

## Karpathy 的核心洞察（原文摘）

> "模型会替你做出错误的假设，然后一直推进，不检查、不寻求澄清、不浮现矛盾……过度复杂化代码和 API……有时会改动不充分理解的代码"
>
> "给 LLM 成功标准而非指令清单，让它循环迭代直到达成目标"

这两句话精准捕捉了 LLM 在编码协作中**最常见的四种失败模式**。本准则就是针对这四种失败的对应解药。

---

## 四条原则（每条都有：定义 / 反模式 / 检查点 / 在本 skill 哪些 phase 使用）

### 原则 1：Think Before Coding（先想再写）

**定义**：在动手写代码之前——
- 显式列出**所有未明确的假设**
- 给出**多种可能的解释**（用户的话可能意味着 A 也可能 B）
- 必要时**推回（push back）**用户的描述，问"你说的 X 是不是其实想要 Y？"

**反模式（必拒绝）**：
- ❌ 看到需求就直接 spawn agent 开始写代码
- ❌ 假设默默替用户做掉，不浮现给用户
- ❌ 看到模糊描述自动用"最常见解释"推进而不问

**检查点**：
- 每个 phase 开始前，问自己："这次任务里，我有几条假设？它们都明确了吗？"
- 假设清单应该被**显性写出来**（不是在脑子里默念）

**在本 skill 哪些 phase 使用**：
- **Phase 1 澄清**：本来就是干这事的，要做到极致
- **Phase 4 架构**：架构决策依赖的假设要写在 `templates/architecture.md` 的"假设检查表"段
- **Phase 7 实施**：每个 spawn 的子 agent 收到任务时，必须**先输出假设列表**再开始写代码
- **Phase 9 审查**：对抗审专门检查"实施时是否做了错误假设并传播下游"

**实操**：
```
spawn 子 agent 实施任务前，prompt 必须包含：
"在开始写代码前，先输出：
 1. 我对本任务的核心假设（5 条以内）
 2. 任何模糊的地方
 3. 多种可能的解释（如有）
 ↓ 等主线程确认/澄清后再开始写"
```

### 原则 1 的操作工具：未知四象限（Unknown-First，先挖未知再动手）

> 来源：用户 2026-07-06 分享的「先挖未知」纪律。定位：原则 1「显式列假设」的**可操作升级**——把"列假设"细化成分四类、各有动作，并补上原则 1 缺的**主动探盲**。

**心法（反直觉钉子）**：卡住长任务的通常不是模型能力，而是**没被言明的未知**。任务越长越自动，模型替你猜得越多、猜错发现得越晚、返工越贵。**模型越强，越会带着自信把你没说清的意图一路跑到黑——强模型需要更多、不是更少的挖未知纪律。**"先想清楚"优先级永远高于"快点出代码"。

**动手前先把要做的事分四类，各按动作处理**：

| 类别 | 含义 | 必须做的动作 |
|---|---|---|
| ① 已知且已言明 | 需求清楚、已写进任务 | 直接做 |
| ② 已知但没写下来 | 心里有、没落到文字 | **停**：写进任务卡 / prompt，别赌"你懂我懂" |
| ③ 伪已决（知道但没真想过）| 看着定了、其实悬着 | **停**：逼出决定——给 A/B/C + 我的推荐，让 PM 拍板 |
| ④ 不知道自己不知道 | 真正的盲区 | **主动探针**：列"这活儿最可能翻车的 3 个点"，先验证再动手 |

**准入门槛**：全部落到 ①、或 ②③ 已跟 PM 确认、④ 已探过一轮，才允许开始写实现代码。

**强度分级（直接复用本 skill 已有 🏃🚶🐢，不新造一套）**：
- 🏃 快车道：一行自检——"有没有 ②③④？没有 → 直接做"
- 🚶 标准：出 3-5 行未知清单，②③ 强制确认后再动手
- 🐢 重型 / 命中风险面（钱·认证·并发·数据完整性·合规）：完整四象限 + **④ 探针强制**，未清零不进实现

**过程中**：长任务拆小步、每步一个可检查点；撞到新的 ②③④ 立即回本表处理，不要"先猜着写完再说"。每次替 PM 做假设，先说"我假设 X，因为 Y"，给叫停机会。

**沉淀（复用 Phase 1 Step 0 召回 + Phase 12.5 回写闭环，不新建机制）**：收尾记一句"这次真正卡住 / 猜错的未知是什么"，按 **④→①** 写回 CLAUDE.md / PRD / 记忆，让同类未知永久消除。

**红线**：绝不对 ②③④ **静默猜测**后直接实现；绝不把"模型很强"当成"可以少想"的理由。

**在本 skill 哪些 phase 用**：Phase 1 澄清（②③ 用 AskUserQuestion 逼决定、④ 用盲区探针）；Phase 6 任务拆解（每个任务卡带未知清单）；Phase 7 实施（spawn 子 agent 前先过四象限，②③④ 未清零不写码）。

### 原则 2：Simplicity First（最简优先）

**定义**：用**能解决问题的最少代码**实现目标。反对——
- 为单一调用点设计的通用接口
- 为想象中的未来需求预留扩展
- 多余的配置项 / 抽象层 / 包装
- 用"设计模式"装点本可以直白写的代码

**反模式（必拒绝）**：
- ❌ "顺便加个 plugin 机制"
- ❌ "考虑到将来可能 X，先抽象一下"
- ❌ "用工厂模式更专业"（如果只有一个产品）
- ❌ 把 30 行的脚本封装成 200 行的 framework

**检查点**：
- 写完代码后问自己："如果直接 inline 这段逻辑，会更难懂吗？"如果不会 → 移除抽象
- "这个配置项有几个真实用例？"如果 < 2 → 删掉配置项，硬编码当前值

**在本 skill 哪些 phase 使用**：
- **Phase 4 架构**：技术选型对比时拒绝"为未来扩展性引入大库"
- **Phase 7 实施**：spawn 的子 agent 必须遵守此原则
- **Phase 8 代码债**：**维度 2「过度抽象」直接以此原则为准绳**
- **Phase 9 审查**：对抗审打"可维护性"分时按此原则扣分

**实操 · 懒惰梯（The Ladder，写代码前按序过 7 层，停在第一个适用层）**：
1. 这真的需要被造出来吗？（YAGNI）
2. 本代码库里已经有了吗？→ 复用现成的 helper / util / 模式
3. 标准库已经能做吗？→ 用标准库
4. 平台原生特性能覆盖吗？→ 用平台特性
5. 已装的依赖能解决吗？→ 用已装依赖
6. 能一行搞定吗？→ 写成一行
7. 以上都不行 → 才写最小可工作代码

**关键约束**：最短可工作 diff 获胜——但前提是先理解了问题。

**实操（抽象与配置）**：
- 每个新引入的抽象都要写出"为什么不 inline"的理由
- 每个新引入的配置项都要写出"什么场景会用 != 默认值"
- 看到"factory of factories"立刻警惕

### 原则 3：Surgical Changes（手术式改动）

**定义**：**只改动完成任务必须改的部分**，对其他代码保持现状——
- 既有代码风格 / 命名 / 缩进 / 组织方式都保留
- 看到"顺便能优化"的地方不要顺便优化
- 不要重新格式化整个文件
- 不要为了"统一性"改与本任务无关的地方

**反模式（必拒绝）**：
- ❌ "顺手把整个文件重新格式化了"
- ❌ "看到 utils 里命名不一致，统一改了一遍"
- ❌ "把所有 var 改成 const"（如果项目里两种都有）
- ❌ "顺便升级了一下依赖"
- ❌ "把单引号都改成双引号"
- ❌ 改动 PR diff > 实际任务需要的 2 倍

**检查点**：
- 提交前看 diff：每一行改动都能映射到 PRD 里的某条 AC 吗？如果不能 → revert
- "这个改动与本次任务有关吗？" 不有关 → revert
- "如果我把这个改动单独提一个 PR，PM 会通过吗？" 不会 → revert

**在本 skill 哪些 phase 使用**：
- **Phase 7 实施**：spawn 子 agent 必须**显式被告知**不要顺手优化
- **Phase 8 代码债**：发现的"顺手清"也要严格判断"是否真的同区域 + 小成本"，不要藉机大改
- **Phase 9 审查**：对抗审专门检查"diff 里有多少是本次任务无关的改动"

**实操**：
- spawn agent prompt 末尾必加："只改本任务必需的代码，不要顺手优化无关部分。如果发现其他地方有问题，记到 backlog 而不是直接改。"

### 原则 4：Goal-Driven Execution（目标驱动 + 循环验证）

**定义**：给 LLM **可验证的成功标准**（"通过 X 测试 + Y 性能"），而不是指令清单（"做 A 然后 B 然后 C"）。让 LLM 循环迭代直到达成目标。

**反模式（必拒绝）**：
- ❌ "做完一步报告一次，由我决定下一步"（剥夺 LLM 的循环能力）
- ❌ "不给验证标准就写代码"（不知何时停）
- ❌ "代码写完即任务完成"（没跑测试就 claim done）
- ❌ "测试挂了改测试让它过"（goal 不是 test pass，是 functionality work）

**检查点**：
- 每个任务开始前：成功标准是什么？（具体到可测）
- 写完代码 → 跑验证 → 失败 → 改 → 再跑，直到通过
- 真正的 goal 不是"代码写好了"，而是"功能能用 + 测试通过 + 验收达成"

**在本 skill 哪些 phase 使用**：
- **Phase 6 任务分解**：每个任务必有"验收点"列（已在 task-breakdown 模板里）
- **Phase 7 实施**：spawn agent 时给"成功标准"（如 "AC1.1 通过 + 单测通过"）让它自己循环
- **Phase 10 验收**：本来就是 goal-driven 的体现，5 层验收 = 多维度 goal
- **Phase 7 过夜跑**：`/loop /autodev-iterate` 配合 `verification-loop` 是这条原则的完美落地

**实操**：
```
spawn agent prompt 必含：
"成功标准：
 - PRD AC[编号] 全部通过
 - 单元测试 [测试文件] 通过
 - lint + typecheck 0 错误
请循环迭代直到全部达成，达成前不要 claim done。"
```

### 补充战术：Bug Fix = 修根因，不修症状

**定义**：修 bug 时不停在表面症状，往下挖到共享根因——
- **grep 你要改的函数的所有调用方**，如果多个调用方都会踩同一个坑，在**共享函数处修一次**，而不是每个调用方各打一个补丁（一处 guard 的 diff 比 N 处补丁更小、更不易漏）
- 修完自问："同类问题还会从其他调用路径冒出来吗？"

**反模式（必拒绝）**：
- ❌ 只在报错的那个调用点加 if 判空，其他 5 个调用点原样留着
- ❌ 测试挂了就改测试让它过（goal 是 functionality work，不是 test pass）

**在本 skill 哪些 phase 使用**：Phase 7 实施（修复类 task）、Phase 9 审查（检查"修的是根因还是症状"）；autodev-iterate 的根因定位步骤与此配套。

## 与现有原则的整合关系

本 skill SKILL.md 已有"五条核心原则"（关卡守门 / 文档先于代码 / 本机优先 / 业务规则显性化 / PM 视角友好）。它们和 Karpathy 4 原则的关系：

| 我的原则 | Karpathy 原则 | 关系 |
|---|---|---|
| 关卡守门 | Goal-Driven Execution | 互补：关卡是"PM 维度的目标"，goal-driven 是"代码维度的目标" |
| 文档先于代码 | Think Before Coding | 同向：文档化 = 显性化假设 |
| 本机优先 | Simplicity First | 同向：不重新发明轮子 |
| 业务规则显性化 | Think Before Coding | 同向：前者管业务规则，Karpathy 管代码假设 |
| PM 视角友好 | — | 我独有 |
| — | Surgical Changes | Karpathy 独有，关键补充 |

**结论**：两套原则不冲突，深度互补。Karpathy 补全了我现有原则**对代码动作的具体约束**。

## 全局自检（每个 phase 结束前问自己）

1. **Think**：本 phase 有没有"默默替用户做了假设"的情况？显性写出来了吗？
2. **Simplicity**：有没有引入"为想象中需求"的抽象 / 配置 / 包装？
3. **Surgical**：本 phase 的改动有没有超出任务所需的范围？
4. **Goal-Driven**：本 phase 有没有明确的"达成"判定？是不是有可测验证？

任一答"有问题" → 暂停，处理后再 sign-off。

## 与 LLM 安全的关系

本准则**不是安全审查**（那是 `integrations/owasp-llm-2025.md` 的事），而是**编码动作准确性**。两者并行使用：
- OWASP LLM Top 10 → 防"LLM 被攻击 / 输出失控"
- Karpathy 4 原则 → 防"LLM 自身写错代码 / 过度发挥"

Phase 9 审查的对抗审视角应同时跑这两套。

## 反模式速查（一行版本）

- ❌ 不要不浮现假设
- ❌ 不要预留未来扩展（写码前先过懒惰梯 7 层）
- ❌ 不要顺手优化无关代码
- ❌ 不要不给成功标准
- ❌ 不要修症状不修根因（grep 所有调用方，共享处修一次）
- ❌ 不要对 ②③④ 未知静默猜测就实现（先挖未知：②③写下来跟 PM 确认、④列翻车点先验）

记不住？记住这六个"不要"。
