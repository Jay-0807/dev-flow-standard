## 4. 核心用户故事（每条挂证据来源）

> ⛔ 不允许 PM 凭空写 user story。每条必须挂"为什么这条 priority 是 P0"的证据来源。

| 编号 | 故事 | 优先级 | 证据来源 | 对应用户画像 |
|---|---|---|---|---|
| US1 | As a [角色], I want [动作], so that [价值] | P0 | 01.5 痛点#1（频次 5次/天，强度 5）| Persona A |
| US2 | ... | P1 | 01.5 痛点#3 + 工单#XX | Persona B |
| US3 | ... | P2 | 竞品反馈调研 | Persona A |

**填表规则**：
- P0 必须挂"频次×强度"证据
- P1 必须挂用户访谈/工单/竞品任一
- P2 可凭 PM 判断但要标注"假设性优先级，待 Phase 12.5 早晨复盘（真人用户验收角色）验证"

## 5.5 假设检查表（Karpathy "Think Before Coding" 必填段）

> 这一段强制 PM 与 PRD 撰写者**显性化所有假设**，防止"默默推进"导致后续返工。每条假设必须列出，并标注是否需要在进入架构阶段前验证。

### 5.5.1 业务侧假设
| # | 假设描述 | 依据 | 是否需要验证 | 验证方式 |
|---|---|---|---|---|
| BA1 | 用户在 [场景] 下会主动 [动作] | [访谈 / 数据 / 直觉] | 是 / 否 | 用户访谈 / 数据查询 |
| BA2 | [假设] | | | |

### 5.5.2 技术侧假设
| # | 假设描述 | 依据 | 是否需要验证 | 验证方式 |
|---|---|---|---|---|
| TA1 | 现有 [模块] 可以扩展支持本需求 | [代码 review / 历史经验] | 是 / 否 | engineering-codebase-onboarding-engineer 摸底 |
| TA2 | [假设] | | | |

### 5.5.3 多种可能的解释（如有）
PM 描述的需求里有以下可能有多种解释的地方，需要确认：

| # | 原描述 | 解释 A | 解释 B | 已确认是 |
|---|---|---|---|---|
| AMB1 | "支持多店铺" | 一个用户可以切换多个店铺 | 一个店铺可以多人共管 | A / B / 都做 |

### 5.5.4 主动 push back（如果 PM 表述有矛盾或不合理）
- 我观察到 [PM 表述 X] 与 [前置约束 Y] 可能冲突，建议确认/修正：[具体修改建议]
- ...

**填表硬性要求**：业务/技术假设各至少 3 条，模糊解释至少识别 1 条，否则 PRD 不予通过。
