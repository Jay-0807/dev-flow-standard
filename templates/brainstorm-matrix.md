## §3：CONVERGE 决策（`02.5-brainstorm-converge.md` 主体）

```markdown
## 选定方案: 方案 D <短标题>

**总分**: 17/20
**关键加分**: 调研对齐 + 需求覆盖双高

---

## 选这个方案的具体理由（≥ 3 条）

1. **需求覆盖 5/5**: PRD AC 1-10 全覆盖（A 方案也是 5，但 D 兼有 B 的边缘场景）
2. **调研对齐 5/5**: 01.5 §3 用户旅程明确"先实时同步算一遍，再用规则微调"——D 方案的"混合"思路精准对应
3. **平衡风险**: A 方案实时同步计算成本高，C 方案规则太死板；D 方案核心走实时同步 + 边缘走规则，兼得灵活和可控

---

## 各被否方案的具体理由

### 方案 A 否决理由
- 长期维护成本太高（实时同步计算线性增长 + 难预测）
- 调研对齐虽然 5，但"全实时同步"在 01.5 §5 用户疼痛"系统不稳定"上有风险

### 方案 B 否决理由
- 需求覆盖仅 4（PRD AC 8 "实时根据最新数据刷新"用预计算难做）
- 调研对齐仅 3（用户期望"实时"而非"次日生效"）

### 方案 C 否决理由
- 调研对齐仅 4（用户期望实时而非纯静态规则）
- 长期维护虽然 5，但规则爆炸（业务复杂时 100+ 条规则不可维护）

---

## 给 Phase 3 影响面的输入

选定方案 D 涉及：
- 新增模块：ComputeRouter（路由"用实时同步还是规则"）
- 改既有：ExportService（加 hybrid 模式）
- 新增表：compute_rules + compute_cache
- 集成：外部数据源 API + 内部规则引擎

---

## 给 Phase 4 架构的种子

选定方案 D 的关键设计点：
- Compute Router 用什么策略？（按数据类目 / 按数据规模 / 按时间窗口）→ Phase 4 决定
- 实时同步计算失败 fallback 到规则引擎？→ Phase 4 决定
- 缓存层用 Redis 还是 LRU memory？→ Phase 4 决定

---

## 决策对通用工程原则的对齐

- 业务规则显性化: 规则部分进 `compute_rule` 表（而非硬编码）
- 人工保留点: 实时同步计算结果 confidence < 0.7 时强制 human_review
- 数据来源标注: 每次计算响应含 `data_source: "realtime" / "rules" / "hybrid"`
- LLM API 元数据三字段（置信度 / 人工复核标记 / 数据来源）：仅适用 AI 原生项目（非 AI 项目不强制）
```

**触发情境**: Phase 2.5 brainstorm 评估 4 个候选方案

**候选**:
- A: 实时同步计算
- B: 预计算 + 缓存
- C: 规则引擎

**依据**:
- 评分矩阵 17/20 最高

**影响范围**: 新增 1 模块 + 2 表，改 1 既有模块

**可逆性**: ⚠️ 部分可逆（compute_rules 表加了不好回滚）

**checkpoint**: ✅ 触发（重要架构决策）

**PM 早上需要 review 的点**: 是否同意"混合"思路。如选 A 或 C，需 redo Phase 3+。
