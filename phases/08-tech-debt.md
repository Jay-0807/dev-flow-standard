# 🧹 代码债扫描

> 内部编号：Phase 8  |  独立命令：/u-debt
> 模式：🤖 Autonomous（9 维度扫描 + 顺手清理建议）

## 目标
对本次实施改动的代码做**9 维度技术债审计**，识别"顺手能清的债"和"现在不清以后会更贵的债"。

## 输入
- `iteration-vault/07-implementation-log.md`
- 主分支上本次改动的所有 diff
- `integrations/tech-debt-9d.md`（本 skill 内化的 9 维度审计精华）
- `templates/tech-debt-audit.md`
- `principles/karpathy-llm-coding.md`（**必读**：维度 2「过度抽象」按 Simplicity First 判定；diff 范围按 Surgical Changes 校验）

> **Karpathy 加权检查**：
> - 维度 2「过度抽象」一票否决——发现任何"为想象中未来需求"引入的抽象/配置/包装，立刻标红
> - 额外维度 X「无关改动」（不计入 9 维度但单独列）：本次 diff 里与 PRD AC 无映射的改动 = Surgical Changes 违反 = 必须 revert

## 工作流（3 步）

**Step 1：调 simplify 跑一遍轻审查**
触发：`simplify`（本机内置）。
针对本次改动让它给出"复用 / 简化"建议。这一步是粗筛。

**Step 2：按 9 维度做深度审计（核心）**
Read `integrations/tech-debt-9d.md`，按其中的 9 维度对本次代码做扫描。9 维度是：

1. **重复代码**：与现有 utils / hook / service 重复实现的逻辑
2. **过度抽象**：为单一调用点设计的过度通用接口
3. **缺失测试**：新增 / 修改的函数没有对应测试
4. **错误处理缺失**：catch 块为空、错误吞掉、缺乏用户可见反馈
5. **硬编码**：本应配置化的常量、URL、阈值
6. **过期依赖**：本次引入了已被 deprecate 的库
7. **性能反模式**：N+1、全表扫描、大 list re-render、内存泄漏
8. **可读性**：超长函数（>100 行）、嵌套 > 4 层、命名不清
9. **耦合度**：跨模块直接访问私有字段、循环依赖、单例滥用

对每一维度，列出本次改动中的具体债项 + 修复成本评估（小 < 30min / 中 < 2h / 大 ≥ 半天）。

**Step 3：分级 & 决策建议**
对每项债，给一个标签：
- 🟢 **顺手清**（小成本 + 同区域改动）：本次 sprint 内顺手修
- 🟡 **下次清**（中成本 / 需要单独测试）：进 backlog，下个 sprint 处理
- 🔴 **战略级**（大成本 / 跨模块影响）：单独立项，与 PM 讨论 ROI

最终给 PM 看的版本：
- 顺手清的：本 skill 自动追加任务到 Phase 7 残留项里，跑掉
- 下次清的：写入 `iteration-vault/08-tech-debt-audit.md` 的"Backlog 候选"段
- 战略级的：突出标红，请 PM 决定是否立项

```
代码债审计完成。
- 本次新增债：[低 / 中 / 高]
- 已顺手清掉：[N] 项
- 进 backlog：[N] 项
- 需要 PM 决策的战略级债：[N] 项（详见 08 报告）

```

## 关卡处理
本阶段**不是** ⛳ 关卡。但若发现战略级债项 ≥ 3 个，建议 PM 单独看一眼，避免债务雪球。

## 失败回退
- 若 9 维度扫描后发现本次改动整体质量不达标（如 > 10 项中高级债）→ 不进入 Phase 9，建议先回到 Phase 7 重做关键任务
- 若与本次需求无关的债被发现（如改 A 模块时看到 B 模块有大问题）→ 记到一个独立的"代码债日记"文件，不混入本次报告

## Standalone 模式

可独立触发：`/u-debt`
不依赖主流水线，对当前工作目录 + 当前 git HEAD 跑 9 维度代码债扫描。
输入解析：自动识别项目类型（Web/SaaS/AI）+ 技术栈
输出：单跑模式写 `.u-debt-report-<timestamp>.md` 到当前目录。
发现高严重度债 → 同时写 DEBUG-TRACE.md。
适合：接手老项目第一步先扫一遍 / 季度技术债审计。
