# 📐 影响面分析

> 内部编号：Phase 3
> 模式：🤖 Autonomous（代码库现状勘察 + 影响面分析 + ADR 记录）

## 目标
让 Claude 在动手前先**摸清楚**：当前代码库里哪些模块会被本次需求影响，哪些接口要改，哪些数据表要动，会不会触发回归风险。给架构师视角的依据。

## 输入
- `iteration-vault/02-PRD.md`（确认通过的 PRD）
- 当前工作目录的代码库（默认 项目根目录）
- `templates/impact-analysis.md`

## 工作流（3 步）

**Step 1：调 engineering-codebase-onboarding-engineer 摸底**
用 Agent 工具：`subagent_type: "engineering-codebase-onboarding-engineer"`，喂给它的 prompt：

```
任务：基于以下 PRD，扫描当前代码库，识别出会被本次需求影响的所有模块、接口、数据表、配置项。
PRD 内容：[贴 02-PRD.md 全文或核心段]
输出：
1. 直接影响模块清单（路径 + 文件 + 函数级）
2. 间接依赖模块（通过 import / API 调用 / 共享状态）
3. 涉及数据表 / Schema 变更
4. 涉及环境变量 / 配置文件
5. 共享的工具函数 / utils
6. 可能的回归风险点（哪些既有功能会因为本次改动可能挂掉）
请按 templates/impact-analysis.md 的格式输出。
```

**Step 2：交叉验证（用 Grep + Glob 抽样核实）**
agent 给出的影响面列表可能漏或假。本 skill 在主线程做抽样验证：
- 对 agent 列出的 top 5 关键文件，用 Grep 查它们被 import 的位置
- 对涉及的 API 路径，用 Grep 查它们在前后端的所有引用点
- 对数据表，看是否有迁移文件需要同步

发现遗漏 → 追加到清单，标"主线程补"。

**Step 3：风险分级**
对每个影响点打标签：
- 🟢 **低风险**：纯加法（新增独立文件/路由），不动既有逻辑
- 🟡 **中风险**：扩展既有接口/字段，需要兼容旧调用
- 🔴 **高风险**：修改既有逻辑/破坏性 schema 变更，需要数据迁移 + 全量回归

## 产出

**文件**：`iteration-vault/03-impact-analysis.md`（用 templates/impact-analysis.md）

核心内容：
```markdown
# 影响面分析: <feature-name>

## 直接影响（agent 识别 + 主线程核实）
| 文件路径 | 函数/区块 | 影响类型 | 风险等级 |
|---|---|---|---|

## 间接依赖
...

## 数据库变更
- 新增表 / 字段：
- 修改字段：
- 迁移脚本是否需要：

## 配置 & 环境变量
- 新增：
- 修改：

## 回归风险
- 高风险点 1：<描述> + 建议覆盖测试

## 实施顺序建议
- 先动 [X]，再动 [Y]，最后动 [Z]，原因：依赖关系
```

**对 PM 的摘要**（口头）：
```
影响面分析完成。本次改动：
- 涉及 [N] 个文件、[M] 个接口、[K] 个数据表
- 风险分级：🔴 高风险 [N1] 个、🟡 中风险 [N2] 个
- 主要回归风险：[1-2 个最值得 PM 知道的]
现进入架构设计阶段。
```

## 关卡处理
本阶段**不是**⛳关卡。但若发现严重风险（如 PRD 里写的功能与现有架构根本冲突），暂停并升级到"PRD 需要重做"，回到 Phase 2。

## 失败回退
- agent 无法理解代码库（非 项目或代码非常陈旧）→ 提示 PM 先跑一次 `/autodev-reverse` 反向生成文档
- 影响面过大（> 50 个文件）→ 建议把本次需求拆成 2-3 个小迭代
